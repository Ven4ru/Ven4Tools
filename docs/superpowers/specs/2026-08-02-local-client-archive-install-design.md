# Установка клиента из локального файла (лаунчер)

**Дата:** 2026-08-02
**Статус:** утверждено пользователем, готово к планированию реализации

## Проблема

Лаунчер умеет распаковывать zip-архив клиента только внутри собственного пайплайна загрузки (`MainWindow.Download.cs` → `SafeZipExtractor.ExtractAsync`) — скачал сам, проверил SHA256 по подписанному `version.json`, распаковал. Нет способа «указать лаунчеру уже лежащий на диске zip клиента» — ни через UI, ни через командную строку.

Два реальных сценария, где это нужно:
1. **Ручное/скриптовое разворачивание** — лаунчер и клиент доставлены на машину отдельно (например, удалённо через SSH/scp), клиент лежит в `Downloads`, но лаунчер его не подхватывает — нужно вручную распаковывать архив самостоятельно.
2. **Проблемы с сетевой загрузкой у лаунчера** — источник заблокирован/троттлится/недоступен именно для лаунчера, но пользователь способен скачать тот же архив другим путём (браузер, VPN) и хочет отдать его лаунчеру.

Оба сценария сейчас упираются в один и тот же тупик: «есть архив на диске — лаунчер с ним ничего сделать не может».

## Требования к безопасности

Вся текущая модель доверия лаунчера — fail-closed: zip принимается только если его SHA256 совпадает с тем, что указано в ECDSA-подписанном `version.json`. Локальный файл, полученный не через собственную загрузку лаунчера, этой гарантии не имеет — значит для него нужен отдельный, но не более слабый механизм проверки.

## Архитектура

### Два независимых хеша

Никаких изменений в существующем сетевом пути загрузки — он как сверял whole-file `SHA256` архива с `version.json`, так и будет. Добавляются два новых независимых механизма поверх:

- **`H_canonical`** — канонический хеш содержимого архива БЕЗ записи с подписью: детерминированный список (имя файла, байты) всех файлов архива, кроме `_ven4tools_signature.json`, в фиксированном порядке (сортировка по `FullName`, порядковое сравнение). Существует только для офлайн-подписи внутри zip, никуда за пределы архива не публикуется. Нужен именно канонический хеш (а не хеш всего файла целиком), чтобы избежать циркулярности: подпись, добавляемая как запись ВНУТРЬ архива, не может быть подписью хеша ЭТОГО ЖЕ архива, включающего её саму.
- **Отзыв (revocation)** — по обычному whole-file `SHA256` (той же величине, что уже публикуется в `version.json` для сетевой загрузки) — короткий deny-list уже выпущенных, но впоследствии отозванных версий, а не allow-list истории всех версий.

### Новая утилита подписи — `Tools/ClientArchiveSigner`

По образцу уже существующих `Tools/CatalogSigner`, `Tools/UpdateManifestSigner`, `Tools/NotificationsSigner` — тот же принцип: домен-сепаратор в подписываемых байтах (`"Ven4Tools.ClientArchive.v1\n"`) + отдельный, выделенный именно под этот тип артефакта приватный ключ (паттерн проекта — не переиспользовать ключи между типами артефактов).

Режимы работы (аналогично `UpdateManifestSigner`):
```
ClientArchiveSigner <archive.zip> <private-key.pem>
ClientArchiveSigner verify <archive.zip> <public-key.pem>
```

Порядок при релизе (встраивается в `ven4tools-release` skill, шаг сразу после сборки zip, до `gh release create`/`cdn-deploy`):
1. Собрать zip клиента как обычно (`dotnet publish` + `Compress-Archive`) — без изменений.
2. `ClientArchiveSigner <archive.zip> <private-key.pem>`:
   - считает `H_canonical` по всем текущим файлам архива;
   - подписывает `DomainSeparator + H_canonical`;
   - дописывает в тот же zip новую запись `_ven4tools_signature.json` = `{ "sha256_canonical": "...", "signature": "...", "version": "X.Y.Z" }`.
3. **Только после этого** считается whole-file `SHA256` для `version.json` — как и сейчас, просто исходный файл на одну запись длиннее (существующий шаг публикации не меняется, просто выполняется над файлом postfactum).
4. Публичный ключ (`ClientArchiveSigner`) зашивается в лаунчер как embedded-ресурс, аналогично `EcdsaManifestVerifier`.

### `version.json` — новое поле `revokedClientHashes`

```json
{
  "client": { "version": "...", "sha256": "...", ... },
  "launcher": { ... },
  "revokedClientHashes": []
}
```
Пустой по умолчанию. Заполняется вручную только если конкретный опубликованный архив нужно отозвать задним числом (например, найдена критическая уязвимость в уже выпущенной сборке). Поле входит в уже подписываемый `version.json` — отдельного ключа/файла/подписи не требуется, используется существующий `UpdateManifestSigner`/`EcdsaManifestVerifier` пайплайн без изменений в его механике.

### Сервис проверки — `LocalArchiveVerifier` (новый, `Ven4Tools.Launcher/Services/`)

Поток проверки при установке из локального файла:

```
Открыть zip → прочитать `_ven4tools_signature.json`
  ├─ отсутствует/повреждена запись → отказ,
  │    "архив без офлайн-подписи, установка отменена"
  └─ есть →
      Пересчитать H_canonical по остальным файлам архива
      Проверить ECDSA-подпись (встроенный публичный ключ) →
        невалидна → отказ, "подпись не совпадает — архив изменён или повреждён"
        валидна → офлайн-гарантия подлинности получена

Если есть сеть (best-effort, короткий таймаут ~3-5 сек):
  Скачать/сверить version.json + .sig (существующая проверка EcdsaManifestVerifier)
  whole-file SHA256 этого локального архива ∈ revokedClientHashes?
    да  → отказ, даже с валидной офлайн-подписью:
           "эта версия отозвана — скачайте актуальную через обычную загрузку"
    нет → доверяем
  сеть недоступна/таймаут → шаг пропускается молча, офлайн-подписи достаточно
    (эта часть проверки НЕ блокирующая — иначе офлайн-сценарий 2 из требований
    перестаёт быть офлайн)

Обе проверки (или только офлайн, если сети нет) пройдены →
  SafeZipExtractor.ExtractAsync (тот же путь распаковки, что у сетевой загрузки,
  без изменений) → тот же общий код завершения установки
  (TransactionalDirectoryInstaller + учёт версии), что и у обычной сетевой загрузки —
  единый путь после проверки, чтобы не плодить два параллельных места с риском
  разойтись друг с другом (тот же класс бага, что был найден и исправлен в
  InstallationService.Choco.cs/.Winget.cs в раунде аудита 2026-08-02).
```

### UI-вход

Кнопка «Установить из файла...» на экране загрузки клиента, рядом со штатной кнопкой сетевой загрузки. `OpenFileDialog` с фильтром `*.zip`. Дальнейший визуальный язык — тот же прогресс-бар/лог, что при сетевой загрузке, с этапами: проверка подписи → проверка отзыва (если сеть есть) → распаковка → готово. Ошибки на любом из этапов — тот же стиль сообщений, что уже используется в `MainWindow.Download.cs` (см. пример с "Целостность не подтверждена").

### CLI-вход

```
Ven4Tools.Launcher.exe --install-from=<path> [--silent]
```

Первый в истории лаунчера разбор аргументов командной строки — сейчас `App.xaml.cs::OnStartup` их не читает вообще (проверено). Добавляется минимальный парсер прямо там, перед стандартной инициализацией окна.

С флагом `--silent`: никаких окон/диалогов — весь прогресс через `AddLog`/файловый лог лаунчера, код выхода процесса отражает итог (`0` — успех, ненулевой — конкретная причина отказа). Закрывает сценарий 1 (ручное/скриптовое разворачивание) одной командой вместо самодельного PowerShell-скрипта с scp.

## Тестирование

**Юнит-тесты (`Ven4Tools.Tests`):**
- `LocalArchiveVerifierTests`: валидная подпись проходит; подмена любого байта payload → отказ; отсутствующая `_ven4tools_signature.json` → отказ; whole-file хеш в `revokedClientHashes` → отказ даже при валидной офлайн-подписи; сеть недоступна (таймаут) → офлайн-подписи достаточно, установка продолжается.
- `ClientArchiveSignerTests` (аналогично существующим тестам `CatalogSigner`/`UpdateManifestSigner`): детерминированность `H_canonical` (одинаковый набор файлов в разном порядке добавления в архив даёт тот же хеш), `verify`-режим CLI.

**UI-тест (`Ven4Tools.UITests`, лаунчер):** happy path — кнопка «Установить из файла» на заранее подготовленном подписанном тестовом архиве, полный путь от выбора файла до завершённой установки.

## Не входит в объём (сознательно)

- **Setup.exe лаунчера** — не покрывается этой фичей. Это уже самодостаточный NSIS-установщик (`/S` для тихой установки), новая проверка не решает там никакой реальной проблемы, которой не было бы уже закрыто существующей SHA256-проверкой self-update.
- Никаких изменений в существующем сетевом пути загрузки/проверки — только новые, отдельные механизмы поверх.
